KeyVolution.

An ESP32 smart lock controller designed to connect physical access methods with local configuration and remote management.

ESP32ESP-NOWArduino frameworkLittleFSWebServerTelegram Bot

This page is based on the supplied project documentation. It describes the documented design; add your own build photos and test evidence to show which functions were implemented and verified.

01 / OVERVIEW

Access control across multiple interfaces.

KeyVolution is documented as an ESP32-based smart lock controller. It combines local physical access inputs with a web interface, a Telegram bot, and a second device that scans RFID cards and communicates over ESP-NOW.

Physical access

Capacitive touch input and RFID scans from a separate scanner node.

Remote control

Telegram commands for lock state, status, access keys, and event history.

Local dashboard

Browser-based settings, registered keys, access logs, and auto-lock configuration.

Persistence & updates

LittleFS storage for settings and logs, plus OTA firmware updates through the web interface.

02 / SYSTEM ARCHITECTURE

Two devices, separate responsibilities.

The documentation identifies a main controller and an external RFID scanner node called “Box 1”.

The scanner sends a message containing a message type and an RFID UID. The main controller can respond with status codes for accepted, blocked, or denied scans. The documentation also describes ping and Wi-Fi channel synchronisation messages.

This is a high-level representation of the documented architecture, not a verified network capture or security audit.

04 / SOFTWARE & FEATURES

More than a relay toggle.

Web interface

  • View lock and override status.
  • Manage RFID UIDs, names, and master/temporary privileges.
  • Configure auto-lock timers, timezone offset, audio settings, and melodies.
  • Review the latest 150 access logs and system events.
  • Configure Wi-Fi and update firmware through OTA.

Telegram bot

The documented command set includes /status, /lock, /unlock, /history, /listkeys, /addkey, /revokekey, /scanner, and /reboot. The guide specifies authentication through /login.

Storage

LittleFS is used to retain configuration, logs, and registered key caches across reboots and power loss.

06 / ENGINEERING CONSIDERATIONS

What I would document next.

A project case study is strongest when it includes evidence and limitations, not just a feature list. The supplied guide describes the intended system, but it does not independently establish test coverage or security properties.

  • Validation: record which access methods were tested and what happened during failure cases.
  • Security: review default setup credentials, bot authentication, key handling, and transport protections before real-world deployment.
  • Reliability: test power loss, router changes, scanner disconnection, and recovery behaviour.
  • Physical safety: verify the relay driver, solenoid power requirements, flyback protection, and manual override.
  • Evidence: add photographs, screenshots, serial logs, and a short demo of the actual build.

These are suggested areas for further documentation, not claims that the project has passed those tests.
